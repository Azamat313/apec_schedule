# Архитектура платформы «АПЭК Digital»

Единая цифровая платформа колледжа АПЭК Петротехник. Заменяет старый монолитный
проект `college_schedule`: модуль расписания очищен от лишнего и стал одним из
модулей платформы, вокруг него строятся новые модули с мобильными приложениями.

## 0. На чём основан этот документ (обязательно к прочтению)

Исходный код `college_schedule` при проектировании **был недоступен**.
Документ построен на трёх источниках, и степень достоверности разделов разная:

| Раздел | Основание | Достоверность |
|---|---|---|
| Модель данных (§3.1), статусы, типы занятий | Замер по фактической выгрузке `docs/api/schedule.json`: 19 443 записи за 12.01–24.06.2026, 78 групп, 76 преподавателей, пары 1–7 | **Проверено на данных** |
| Набор экранов и эндпоинтов расписания | JS-функции старого просмотрщика `docs/index.html`: `displayDay/Week/MonthSchedule`, `populateDropdowns`, `getStatusInfo`, `loadDataFromDrive` | Выведено из артефакта |
| Что старая система пушит выгрузку в GitHub при каждом изменении | История репозитория: все 50 коммитов — `Auto-sync (schedule_change)` | Выведено косвенно |
| Выбор стека (FastAPI, PostgreSQL, Flutter, FCM), состав новых модулей, циклы разработки | Типовое решение для колледжа | **Предложение, требует согласования** |

**Что это значит на практике.** Модуль расписания можно принимать как есть —
он проверен на ваших данных. Всё остальное — рабочая гипотеза: список новых
модулей отражает типичные потребности колледжа, а не результат анализа ваших
процессов. Перед циклом 1 нужен доступ к исходникам `college_schedule`, чтобы
свериться с реальной логикой (см. §8).

### Замечания к данным, обнаруженные при импорте

- **`completed` и `done`** — два названия одного состояния (114 против 17 437
  записей). Импортер сводит их к `done`; если смысл разный — правило в
  `constants.py:LEGACY_STATUS_MAP` надо изменить.
- **Статуса `planned` в выгрузке нет вообще** — она содержит только прошедшие
  пары. Для мобильного приложения статус будущих пар обязателен, он добавлен
  платформой.
- `substitution` (1055 записей) — отдельный статус, не флаг. Замены и отмены
  вместе дают ~1900 событий за полгода: это и есть нагрузка на push-уведомления.

## 1. Общая схема

```mermaid
flowchart TB
    subgraph clients [Клиенты]
        MS[Моб. приложение «АПЭК Студент»<br/>Flutter]
        MT[Моб. приложение «АПЭК Преподаватель»<br/>Flutter]
        WEB[Веб-портал / админ-панель]
        LEGACY[GitHub Pages виджет<br/>(старый просмотрщик — остаётся как read-only зеркало)]
    end

    subgraph backend [Backend — FastAPI (модульный монолит)]
        AUTH[auth<br/>пользователи, роли, JWT]
        SCHED[schedule<br/>расписание, замены]
        NOTIF[notifications<br/>уведомления, push]
        ANN[announcements<br/>новости/объявления]
        GRADES[grades*<br/>эл. журнал]
        ATT[attendance*<br/>посещаемость]
    end

    DB[(PostgreSQL / SQLite)]
    FCM[Firebase Cloud Messaging]

    MS --> backend
    MT --> backend
    WEB --> backend
    SCHED --> DB
    AUTH --> DB
    NOTIF --> FCM
    SCHED -- "экспорт JSON (совместимость)" --> LEGACY
```

`*` — модули второй очереди: спроектированы, реализуются в следующих циклах.

## 2. Ключевые архитектурные решения

| Решение | Выбор | Почему |
|---|---|---|
| Стиль backend | **Модульный монолит** (FastAPI) | Один деплой, простая эксплуатация в колледже; модули изолированы по папкам и общаются через сервисные интерфейсы — при необходимости любой модуль выносится в отдельный сервис без переписывания |
| БД | SQLite для разработки, **PostgreSQL** в проде | Одна строка в конфиге меняет базу |
| API | REST + OpenAPI (автогенерация схемы) | Мобильные клиенты генерируют API-клиент из `/openapi.json` |
| Авторизация | JWT (access), роли: `student` / `teacher` / `admin` | Единый вход для всех модулей и обоих приложений |
| Мобильные приложения | **Flutter** (одна кодовая база, общий пакет `apec_api`) | Android + iOS из одного кода; два приложения используют общие пакеты |
| Push | Firebase Cloud Messaging через модуль notifications | Уведомления о заменах/отменах — главная ценность для студентов |
| Совместимость | Экспортёр в старый формат JSON GitHub Pages | Старый репозиторий и Google Sites-виджет продолжают работать, их не трогаем |

## 3. Модули

### 3.1 `schedule` — Расписание (ядро, реализован)
Доменное ядро: группы, преподаватели, кабинеты, пары, замены, отмены.
Статусы: `planned` / `done` / `cancelled` / `substitution`,
типы занятий: `theory` / `practice` (см. `schedule/constants.py`).

Что здесь **не** реализуется — генерация HTML, прямые коммиты выгрузки в
GitHub, desktop-UI. Судя по истории репозитория (все коммиты — `Auto-sync`),
это делает текущая система; в новой архитектуре ответственность разделена:
данные — за API, представление — за клиентов, выгрузка — за экспортёр.
*Требует сверки с исходниками `college_schedule`.*

API:
- `GET /api/schedule` — фильтры: группа, преподаватель, дата/период, статус
- `GET /api/schedule/day/{date}`, `GET /api/schedule/week/{date}`
- `GET /api/groups`, `GET /api/teachers`, `GET /api/rooms`
- `POST/PUT/DELETE /api/schedule` (роль admin) — редактирование, замены
- Импортер `importer.py` — разовая миграция данных из старого JSON-формата

События: при изменении/отмене пары модуль публикует событие
`schedule_changed`, на которое подписан модуль `notifications`.

### 3.2 `auth` — Пользователи и доступ (реализован)
Студент привязан к группе, преподаватель — к записи в справочнике преподавателей.
Регистрация по приглашению/коду колледжа, вход по email+паролю, JWT.

### 3.3 `notifications` — Уведомления (реализован каркас)
- Лента уведомлений пользователя (`GET /api/notifications`)
- Регистрация FCM-токена устройства (`POST /api/notifications/devices`)
- Подписка на события `schedule_changed`: замена/отмена пары → уведомление
  всем студентам группы и затронутым преподавателям
- Отправка в FCM — фоновая задача (в проде: очередь / APScheduler)

### 3.4 `announcements` — Новости и объявления (реализован каркас)
Объявления администрации: целевая аудитория (все / группа / преподаватели),
создание — роль admin, чтение — все. Лента в мобильных приложениях.

### 3.5 `grades` — Электронный журнал (2-я очередь)
Оценки по парам: связь «пара из schedule × студент → оценка/комментарий».
Преподаватель выставляет из своего приложения, студент видит свои.

### 3.6 `attendance` — Посещаемость (2-я очередь)
Отметка присутствия по паре (преподаватель отмечает в приложении),
сводки по группе/студенту, автоматические уведомления родителям — 3-я очередь.

## 4. Мобильные приложения (Flutter)

Монорепо `mobile/`:

```
mobile/
  packages/apec_api/      # общий API-клиент (генерируется из OpenAPI)
  packages/apec_ui/       # общая дизайн-система
  apps/student/           # «АПЭК Студент»
  apps/teacher/           # «АПЭК Преподаватель»
```

**«АПЭК Студент»**: расписание своей группы (день/неделя), push о заменах,
объявления, позже — оценки и посещаемость.

**«АПЭК Преподаватель»**: своё расписание, свои замены, позже — журнал
и отметка посещаемости прямо на паре.

## 5. Развёртывание

- `docker compose up` поднимает backend (+ PostgreSQL в проде).
- Один VPS/сервер колледжа достаточен; reverse-proxy — Caddy/Nginx (TLS).
- CI (GitHub Actions): тесты → сборка образа → деплой; отдельный workflow
  периодически экспортирует расписание в старый формат для GitHub Pages.

## 6. Циклы разработки

1. **Цикл 0 (этот)** — архитектура, каркас платформы, рабочий модуль
   расписания на реальных данных, auth, каркасы notifications/announcements.
2. **Цикл 1** — миграция реальной логики редактирования из локального
   `college_schedule` (нужен доступ к исходникам), админ-веб для диспетчера.
3. **Цикл 2** — приложение «АПЭК Студент» (MVP: расписание + push).
4. **Цикл 3** — приложение «АПЭК Преподаватель», модуль grades.
5. **Цикл 4** — attendance, аналитика, кабинет родителя.

## 7. Перенос в новый репозиторий

Старый репозиторий `apec_schedule` не изменяется (ветка `main` нетронута).
Содержимое `platform/` — корень нового репозитория:

```bash
# в новом пустом репозитории apec-platform
git clone --branch claude/project-architecture-redesign-nqqnak https://github.com/Azamat313/apec_schedule tmp
cp -r tmp/platform/* .
git add -A && git commit -m "Initial platform" && git push
```
